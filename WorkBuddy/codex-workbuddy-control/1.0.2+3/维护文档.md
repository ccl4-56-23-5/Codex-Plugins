# WorkBuddy Control 维护文档

## 1.0.2+3 · 2026-11-18

- `open()` 先检查唯一的 WorkBuddy 主窗口。冷启动优先用应用列表中的标识，列表没有匹配项时用 `WorkBuddy.exe`。有明确安装路径时可调用 `open({ executablePath })`，由同一个 Computer Use 接口发起启动与审批。
- 应用审批超时、启动后没有主窗口、无法前台激活、界面尚不可读分别提示。发生已知激活错误时只刷新窗口并尝试一次。失败后清除窗口绑定和旧控件，不重放输入。
- 构建与覆盖安装沿用下述命令。安装后从实际插件缓存加载对应版本的技能，并分别核对启动、前台接管、发送回执和可见答复。

## 1.0.1+2 · 2026-11-16

- 续写：定位发送或停止控件同层的编辑器。5.11.3 有时只报告文档焦点；此时需要从点击后返回的截图确认编辑框内有光标，再调用 `draft(text, { visualFocus: true })`。正常键入后核对草稿及发送按钮；若树仍旧，使用一次编辑器全选触发刷新，避免重复输入。
- 清理：`clearDraft(expectedDraft)` 从同一编辑器重新核对全文，再用真实键盘全选；只有实际选区等于草稿才删除。不能用无障碍值来代替真实清除，否则 Slate 可能在切换任务后恢复原草稿。草稿清空后调用 `stop()`，继续观察取消或完成回执。
- 菜单：用客户端无障碍树中配对的账户菜单和触发器处理已知遮挡。菜单收起后重新定位分组或模型按钮；其他几何问题从最新截图定位，同一截图的坐标不可复用。
- 状态：动作只发一次，短时等待界面。发送以草稿消失及停止按钮出现或消息回执为依据；模型、分组、任务切换建议为 `click(id, { until })` 指定目标状态。返回 `transition: "unconfirmed"` 时继续观察，不能据此重发或宣称成功。
- 从版本根目录执行 `node --test`，包含既有测试及 QA 回归。安装仍用 `Install.ps1` 并以 `codex plugin list --marketplace workbuddy-tools --json` 核实已启用。本机市场按版本隔离，插件标识不变。
- 覆盖安装时，Codex CLI 不允许从新路径直接登记同名市场。安装器先备妥新版，切换原有市场登记并验证启用；若失败，会恢复原登记。
- 现行远端是 `ccl4-56-23-5/CodexBridge`（`WorkBuddy/`）；只替换 WorkBuddy 源码、文档及同渠道发行。上一版历史路径以其发布时为准。

## 1.0.0+1 · 2026-11-15

- `.agents/plugins/marketplace.json` 定义本地市场。`plugins/codex-workbuddy-control` 包含插件清单和技能。
- `workbuddy.mjs` 通过 Codex 的 `@oai/sky` 运行时识别 WorkBuddy 主窗口和当前控件。新任务调用已识别的本机 WorkBuddy 程序及其任务链接。发送前重新读取草稿并比较完整文本。页面切换和提交后等界面状态确认结果。
- 使用 Node.js 24 执行 `node --test tests/workbuddy.test.mjs`。本版本直接运行源码，无构建依赖。封装 Windows ZIP 时带上隐藏的 `.agents`、`.codex-plugin`、本版根目录文档和项目测试。
- `Install.ps1` 将插件源放入当前用户的 `%LOCALAPPDATA%\CodexWorkBuddy\1.0.0+1` 并调用 Codex CLI 安装。再次运行可恢复本版。升级包以版本目录登记同名市场，运行后核对市场源和插件版本。恢复时重新执行相应版本的安装脚本。
- 本机 WorkBuddy 5.11.3 已验证新任务预填、提交、读取完成文本和停止测试。已完成会话的焦点报告在本机不可用，当前版可以读、核对和发送由用户已填入的草稿。无障碍树受 WorkBuddy 窗口布局、语言、版本和界面渲染影响。
- Windows 用户配置、登录和已有 WorkBuddy 数据由宿主管理。插件通过宿主运行时操作界面。GitHub 发布在 `ccl4-56-23-5/Codex-Plugins` 的 `WorkBuddy-Control插件` 目录和对应 Release。
